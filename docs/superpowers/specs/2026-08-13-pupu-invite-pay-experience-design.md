# Pupu 官方代付闭环与全局体验设计

日期：2026-08-13
状态：已批准实施
仓库：`xiaohao300000000-cmd/jiaohu`

## 目标

把当前真实朴朴登录与只读商品能力扩展为完整但受控的购物闭环：

```text
复杂生活需求
→ 选择账号已有收货地址
→ 对应门店真实商品与三道菜方案
→ 用户确认采购清单
→ 真实加入购物车
→ 真实结算预览
→ 用户再次明确确认
→ 创建真实待付款订单
→ 创建官方 invite-pay
→ 展示可点击的朴朴官方付款按钮
→ 用户在官方页面自行决定是否付款
```

首版必须证明付款按钮能打开当前订单的真实官方待付款页面。固定链接、示例链接、仅打开购物车或伪造成功均不算通过。

## 已确认范围

- 使用账号中已有的朴朴收货地址；首版不新增或编辑地址。
- 测试可以真实加入购物车并创建一笔待付款订单。
- 系统不自动支付，用户不付款也可以结束测试。
- 测试后保留当前朴朴登录状态，不退出登录、不删除凭证。
- 最终稳定性测试使用复杂开放需求，而不是单一确定商品。
- 复杂需求连续执行 3 次；前两次只读，第 3 次允许真实加购、创建待付款订单和验证付款跳转。
- 完成闭环后，从首次使用者角度执行一次全局体验测试并修复 Bug 与不合理交互。

## 非目标与资金边界

- 不接触、收集或代理支付密码、银行卡、微信支付或支付宝凭证。
- 不自动点击官方页面的最终支付动作。
- 不把地址、手机号、验证码、支付链接、订单密钥或认证凭证交给 DeepSeek。
- 不允许语言模型直接决定账号、地址路径、订单请求体、审批令牌或支付 URL。
- 不在结果未知时盲目重试订单创建或 invite-pay 创建。
- 不使用 mock 商品、mock 价格或 mock 付款链接完成真实验收。

## 方案选择

### 采用：官方 invite-pay 链路

复用 Pupu CLI 已有的官方链路：结算预览、审批、真实订单、invite-pay 创建、分享信息读取与付款状态查询。优先使用接口真实返回的 HTTPS 分享 URL；若官方只返回小程序 path 或 `pupumall://` Deep Link，则按设备提供对应跳转并做真实点击验收。

### 不采用：仅打开购物车

风险较低，但不能把用户直接带到当前订单的待付款页面，闭环不完整。

### 不采用：自建普通中转付款链接

会增加敏感链接泄露、过期管理和钓鱼误解风险。首版只展示官方返回或由官方 invite-pay ID 构造的受验证官方 Deep Link。

## 一、运行级安全作用域

当前短时账号作用域票据被第一个工具调用删除，导致 Hermes 在同一 Agent 运行中并行调用商品搜索与登录状态时全部得到 `scope_ticket_invalid`。

修正后的规则：

- 一个票据只绑定一个服务端生成的 Agent task/run ID。
- 同一 task/run 内允许多个只读工具并发读取相同票据。
- 不同 task/run ID 不能复用票据。
- 每次读取都重新校验文件类型、0600 权限、身份、账号、允许目录和过期时间。
- 拒绝符号链接、相对路径、账号不匹配和过期票据。
- 票据在运行结束、取消或过期后由服务器精确删除；无效票据立即删除。
- 票据只授权只读工具。购物车写入和真实订单必须使用独立的显式审批能力。

## 二、已有地址选择

地址是商品搜索和下单前的硬门槛，因为门店、库存、价格和配送范围都依赖地址。

流程：

1. 服务端通过已认证账号读取朴朴已有 receiver 列表。
2. 返回给前端的地址为脱敏展示模型，只含 opaque receiver ID、地址标签、区域摘要、门牌摘要和手机号尾号。
3. 完整地址和加密坐标只在受信任服务端/CLI 边界使用，不进入 AI 消息或公开日志。
4. 用户明确选择一个地址后，服务端解析其 store/place 绑定。
5. 后续商品搜索、购物车、结算和订单创建全部绑定该地址与门店。
6. 地址失效或超出配送范围时回到地址选择，不猜测 GPS，不自动换地址。

## 三、复杂需求与采购方案

基准真实需求：

> 我今晚想做一个低脂的三道菜，要步骤简单、营养全面。

Hermes 可以在同一运行中连续或并行调用多个只读工具，搜索蔬菜、蛋白质、主食/配料并检查登录与购物车状态。最终方案必须包含：

- 三道明确菜品；
- 简单步骤与预计耗时；
- 蛋白质、蔬菜和主食/能量来源的营养说明；
- 来自所选门店的真实商品、SKU、规格、实时价格与可售状态；
- 缺货或搜索失败时的替代选项；
- 不把同一食材重复加购。

## 四、加购确认与真实购物车

方案完成后先展示可编辑采购清单。用户点击“确认加入购物车”才执行真实写入。

- 写入前显示商品、数量、规格、单价与预计合计。
- 写入操作绑定当前浏览器会话、账号、地址和方案版本。
- 使用幂等请求 ID，重复点击不能重复加购。
- 写入后读取真实购物车回执，逐项展示成功、数量调整、缺货或失败。
- 第三次真实测试允许保留测试加购商品；不自动清空用户原购物车。

## 五、结算预览与二次确认

加购成功不直接创建订单。系统调用真实 settlement preview 并展示：

- 脱敏收货地址；
- 最终商品与数量；
- 缺货、限购、价格或促销变化；
- 商品金额、优惠、配送费和最终应付金额；
- 预计送达信息；
- 预览有效期。

按钮文案为“确认并创建待付款订单”，并明确说明点击后会真实创建订单但不会自动付款。预览过期或商品、价格、优惠、费用、地址、门店发生实质变化时，旧确认失效，必须重新展示并再次确认。

## 六、真实订单与官方 invite-pay

确认后执行受保护的命令链：

1. 服务端签发一次性、绑定 preview hash、账号、用户和请求 ID 的 `REAL_ORDER` 审批。
2. CLI 重新创建结算预览并验证与获批版本一致。
3. 通过幂等 ledger 创建真实订单。
4. 为该订单创建官方 invite-pay。
5. 读取官方分享 payload 和付款状态。

若网络中断导致结果未知，状态进入 `outcome_unknown`，禁止自动重试；先按请求 ID/订单状态协调后再决定下一步。

## 七、付款按钮与跳转

付款 presentation 只接受经过服务端校验的官方结果：

- 优先：朴朴返回的 HTTPS `shareUrl/url`；
- 次选：官方小程序 path，由支持的系统桥接打开；
- 兜底：绑定真实 invite-pay ID 的 `pupumall://login.pupumall.com/invite_pay/detail` Deep Link。

前端显示“去朴朴官方付款”按钮、应付金额、有效期和当前状态。按钮不自动触发，必须由用户点击。URL 只允许 HTTPS 官方域名或明确 allowlist 的 `pupumall` scheme；拒绝 `javascript:`、data URL、未知域名和模型提供的链接。

点击验收必须证明打开的页面对应当前真实待付款订单。仅渲染按钮、URL 格式正确或启动朴朴首页都不算通过。

## 八、付款状态

通过只读查询展示官方状态：

- `WAITING_PAY`：等待付款；
- `PAY_SUCCESS`：已付款；
- `PAID_BY_OTHER`：已由他人付款；
- `CANCELED`：已取消；
- 已过期或未知状态：明确提示并停止轮询。

轮询需可见、有限频率、页面离开时停止。系统不把状态查询失败误报为付款失败，也不把按钮点击当成付款成功。

## 九、错误与体验文案

不再把所有后端错误统一显示为“服务暂时没有回应”。至少区分：

- 登录已过期；
- 地址不可配送；
- 商品缺货或价格变化；
- 账号安全作用域失效；
- 朴朴服务超时；
- 订单结果未知，禁止重试；
- 官方付款链接缺失或已过期；
- Hermes/DeepSeek 暂时异常。

每个状态提供安全且可执行的下一步，保留已经完成的用户选择，不要求无关步骤重做。

## 十、测试与验收

### 自动化

- 运行级票据并发复用、跨运行拒绝、过期、权限、符号链接与清理；
- 地址脱敏、会话隔离、门店绑定和配送失败；
- 多工具并发与连续 artifact 配对；
- 购物车幂等、部分成功、重复点击和真实回读；
- settlement 物料变化使审批失效；
- REAL_ORDER 审批绑定与一次性消费；
- 订单/invite-pay 结果未知禁止盲重试；
- 付款 URL allowlist、过期与状态映射；
- reducer/presentation/browser 覆盖完整流程和具体错误文案。

### 真实稳定性

同一复杂需求连续执行 3 次：

1. 第一次只读，生成真实三道菜与采购方案；
2. 第二次只读，验证并发/连续多工具和结果稳定；
3. 第三次真实加购，生成结算预览，经用户确认后创建待付款订单，取得并点击真实官方付款按钮，但不要求实际支付。

3 次均不得使用 mock 商品或 mock 付款链接。包含一次服务重启后的登录保留与任务恢复。

### 使用者全局测试

以首次用户身份完整走：需求输入、首次登录、滑块、短信、地址选择、方案理解、修改清单、加购、结算确认、创建订单、付款跳转、错误恢复和返回继续。逐项修复：

- 状态和按钮是否让非技术用户理解；
- 是否出现重复输入、重复确认或丢失上下文；
- 等待过程是否有准确反馈；
- 错误是否具体并可恢复；
- 返回、刷新、重试和重复点击是否安全；
- 手机端布局、滚动、焦点、键盘、触控和 reduced motion；
- UI 承诺是否始终不超过真实后端能力。

## 完成定义

只有同时满足以下条件才算闭环完成：

- 复杂需求连续 3 次通过；
- 真实地址和门店绑定；
- 真实商品和购物车回读；
- 真实结算预览与二次确认；
- 真实待付款订单；
- 官方 invite-pay 链接或 Deep Link 在当前设备点击后打开对应付款页；
- 无自动付款，登录保持；
